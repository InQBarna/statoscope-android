## Create a Reducer

`ScopeConfig` bundles a scope's initial state and the pure function that turns one `State` plus
one event (`When`) into the next `State`. There's no class to subclass and no framework base
type — a reducer is just a `data class` for state, a `sealed interface` for events, and a plain
function between them.

We'll build a counter: two buttons, one running total.

### Step 1 — import the core package

```kotlin
import statoscope.core.Dependencies
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
```

`EffectsState` isn't used until Step 4, and `Dependencies` isn't used until Tutorial 04 — both
are imported here because the import block is the union of everything the finished example
needs, shown once rather than growing line by line at each step (Swift's equivalent tutorial
does the same with a single coarse `import Statoscope`).

### Step 2 — declare the state

`CounterState` is an ordinary Kotlin `data class`. Unlike Swift's `Reducer`, there's no
`inout` in Kotlin — state updates return a *new* `CounterState` via `copy()`, never mutate one in
place.

```kotlin
import statoscope.core.Dependencies
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
/** Tutorial 01: Basic Counter with State and When. */
data class CounterState(
    val viewDisplaysTotalCount: Int = 0
)
```

### Step 3 — declare the events

`CounterWhen` is a `sealed interface` with `data object` cases — Kotlin's closest match to
Swift's parameterless `enum` cases (and to `statoscope-zustand`'s discriminated-union actions).
Sentence-like naming pays off the same way it does in Swift: `userTappedIncrementButton`, not
`increment`.

```kotlin
import statoscope.core.Dependencies
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
/** Tutorial 01: Basic Counter with State and When. */
data class CounterState(
    val viewDisplaysTotalCount: Int = 0
)

sealed interface CounterWhen {
    data object UserTappedIncrementButton : CounterWhen
    data object UserTappedDecrementButton : CounterWhen
}
```

### Step 4 — declare `update`'s signature

`update` is a plain top-level function from `(State, When, EffectsState<When>, Dependencies)` to
a new `State` — no `self`, no instance state to accidentally read or leak, same guarantee
Swift's `static func update` makes by construction. We'll leave the body empty for now.

> **Revised:** this tutorial originally gave `counterUpdate` a 2-parameter signature — no
> `effects` — reasoning that building an effects handle before anything used it would be
> premature. Tutorial 02 turned out to need one on every reducer, so `ScopeConfig`'s `update`
> field grew a third parameter, and this example was updated to match. `counterUpdate` still
> ignores it — nothing here enqueues an effect — but the signature is now stable across every
> tutorial from here on, exactly the tradeoff Swift's own tutorial made from day one.
>
> **Revised again:** Tutorial 04 (Dependency Injection) needed every reducer to be able to
> resolve injected dependencies, so `update` grew a fourth parameter, `dependencies:
> Dependencies`. `counterUpdate` ignores this one too — same reasoning as `effects` above, and
> the same growth pattern: add the parameter, retrofit every existing example to accept (and
> ignore) it, document the change here rather than silently rewriting history.

### Step 5 — implement the logic

Because `counterUpdate` is a pure function, this reads exactly like what it is: a total
computed from an event and a starting point. `counterConfig` wires the function and the initial
state together into a `ScopeConfig` — this is the value you'll actually build a running scope
from.

```kotlin
import statoscope.core.Dependencies
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
/** Tutorial 01: Basic Counter with State and When. */
data class CounterState(
    val viewDisplaysTotalCount: Int = 0
)

sealed interface CounterWhen {
    data object UserTappedIncrementButton : CounterWhen
    data object UserTappedDecrementButton : CounterWhen
}

fun counterUpdate(
    state: CounterState,
    action: CounterWhen,
    effects: EffectsState<CounterWhen>,
    dependencies: Dependencies
): CounterState {
    return when (action) {
        is CounterWhen.UserTappedIncrementButton ->
            state.copy(viewDisplaysTotalCount = state.viewDisplaysTotalCount + 1)
        is CounterWhen.UserTappedDecrementButton ->
            state.copy(viewDisplaysTotalCount = maxOf(0, state.viewDisplaysTotalCount - 1))
    }
}

val counterConfig = ScopeConfig(
    initial = CounterState(),
    update = ::counterUpdate
)
```

## Write tests and acceptance criteria

The `given`/`.on`/`.thenEquals`/`.runTest()` fluent API (`statoscope.testing`) mirrors both
Swift's `GIVEN`/`WHEN`/`THEN` and `statoscope-zustand`'s `given`/`.when`/`.thenEquals` — construct
the scope from a `ScopeConfig` in `given(...)`, dispatch events with `.on(...)`, and assert on
state with `.thenEquals(...)`.

`.on` is the one deliberate rename from both siblings' `.WHEN`/`.when` — `when` is a reserved
keyword in Kotlin. `thenEquals` takes a real property reference (`CounterState::viewDisplaysTotalCount`),
which is statically typed and checked at compile time — closer to Swift's `KeyPath` than
`statoscope-zustand`'s runtime string keys, and a small but genuine Kotlin-specific win.

### Step 1 — the first test

```kotlin
import kotlin.test.Test
import statoscope.testing.given
class CounterTest {

    @Test
    fun testBasicCounterFlow() {
        given(counterConfig)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0)
            .on(CounterWhen.UserTappedIncrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 1)
            .on(CounterWhen.UserTappedDecrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0)
            .on(CounterWhen.UserTappedDecrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0) // Can't go below 0
            .runTest()
    }
}
```

### Step 2 — a second test

Sending the same event repeatedly is a good way to prove acceptance criteria hold over more than
one step, not just the first.

```kotlin
import kotlin.test.Test
import statoscope.testing.given
class CounterTest {

    @Test
    fun testBasicCounterFlow() {
        given(counterConfig)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0)
            .on(CounterWhen.UserTappedIncrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 1)
            .on(CounterWhen.UserTappedDecrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0)
            .on(CounterWhen.UserTappedDecrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 0) // Can't go below 0
            .runTest()
    }

    @Test
    fun testMultipleIncrements() {
        given(counterConfig)
            .on(CounterWhen.UserTappedIncrementButton)
            .on(CounterWhen.UserTappedIncrementButton)
            .on(CounterWhen.UserTappedIncrementButton)
            .thenEquals(CounterState::viewDisplaysTotalCount, 3)
            .runTest()
    }
}
```

We've built the same counter feature as Swift's and `statoscope-zustand`'s tutorials — same
state, same events, same acceptance tests — as a pure function over one immutable state, with no
subclassing and nothing to leak across calls.
