## What is a side effect?

A side effect is any executed code whose result arrives later — the one kind of "later" we
actually want is an asynchronous task. We'll build a counter whose value lives on a remote
server: tapping a button doesn't just update a number locally, it posts the new value and waits
for the server to confirm.

Notice the network call is still split into two events: the trigger
(`UserTappedIncrementButton`) and the result (`NetworkPostCompleted(dto)`). Effects never
bypass the update contract — an effect can only ever report back as another event, dispatched
through the exact same `update` function everything else goes through.

### Step 4 — the effect and the full implementation

`NetworkPostEffect` implements `Effect<CloudCounterWhen>` — its `run()` is a `suspend fun`, so
it can `delay(...)` (standing in for a real network round-trip here) without blocking anything,
and it returns the `When` that reports its result. `update` enqueues one via
`effects.enqueue(...)` instead of a bare self-call, since it's a plain function with no `self`
to call it on — otherwise the shape is identical to Tutorial 01: mutate state synchronously,
enqueue the async work, and let its completion arrive as another event through the same
function.

> **Revised:** Tutorial 04 (Dependency Injection) needed every reducer to be able to resolve
> injected dependencies, so `ScopeConfig`'s `update` field grew a fourth parameter,
> `dependencies: Dependencies`. `cloudCounterUpdate` ignores it — nothing here resolves an
> injected value — same growth pattern documented in Tutorial 01: add the parameter, retrofit
> every existing example to accept (and ignore) it, document the change rather than silently
> rewriting history.

```kotlin
import kotlinx.coroutines.delay
import statoscope.core.Dependencies
import statoscope.core.Effect
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
/** A remote counter's payload — what actually gets persisted, over the network, on each change. */
data class Dto(val count: Int)

/** Tutorial 02: CloudCounter — a counter whose value is stored remotely via a network API. */
data class CloudCounterState(
    val viewDisplaysTotalCount: Int = 0,
    val viewShowsLoadingAndDisablesButtons: Boolean = false
)

sealed interface CloudCounterWhen {
    data object UserTappedIncrementButton : CloudCounterWhen
    data object UserTappedDecrementButton : CloudCounterWhen
    data class NetworkPostCompleted(val dto: Dto) : CloudCounterWhen
}

/**
 * Posts the counter's new value to a remote API. Simulated with `delay(...)` rather than a
 * real network call — safe and deterministic to have running in the background, unlike an
 * unmocked call to a real host.
 */
class NetworkPostEffect(private val newValue: Int) : Effect<CloudCounterWhen> {
    override suspend fun run(): CloudCounterWhen {
        delay(10) // Simulate a network round-trip
        return CloudCounterWhen.NetworkPostCompleted(Dto(count = newValue))
    }
}

fun cloudCounterUpdate(
    state: CloudCounterState,
    action: CloudCounterWhen,
    effects: EffectsState<CloudCounterWhen>,
    dependencies: Dependencies
): CloudCounterState {
    return when (action) {
        is CloudCounterWhen.UserTappedIncrementButton -> {
            val newValue = state.viewDisplaysTotalCount + 1
            effects.enqueue(NetworkPostEffect(newValue))
            state.copy(viewDisplaysTotalCount = newValue, viewShowsLoadingAndDisablesButtons = true)
        }

        is CloudCounterWhen.UserTappedDecrementButton -> {
            if (state.viewDisplaysTotalCount <= 0) return state
            val newValue = state.viewDisplaysTotalCount - 1
            effects.enqueue(NetworkPostEffect(newValue))
            state.copy(viewDisplaysTotalCount = newValue, viewShowsLoadingAndDisablesButtons = true)
        }

        is CloudCounterWhen.NetworkPostCompleted ->
            state.copy(
                viewShowsLoadingAndDisablesButtons = false,
                viewDisplaysTotalCount = action.dto.count
            )
    }
}

val cloudCounterConfig = ScopeConfig(
    initial = CloudCounterState(),
    update = ::cloudCounterUpdate
)
```

Nice — a reducer with effects, same shape as Tutorial 01, still no `self` anywhere.

## Testing effects

The test below is the acceptance criteria for this whole feature. It never actually waits for
`NetworkPostEffect` to run — it manually dispatches `NetworkPostCompleted(...)` right after the
triggering event, exactly the value the real effect would eventually produce. This is
deliberate, not a shortcut: `TestPlan.runTest()` (`statoscope.testing`) never executes enqueued
effects at all, matching both Swift's and `statoscope-zustand`'s testing DSLs — tests stay
deterministic, and you simulate an effect's completion by dispatching its result directly rather
than waiting on real async work.

```kotlin
import kotlin.test.Test
import statoscope.testing.given
class CloudCounterTest {

    @Test
    fun testBasicFlow() {
        given(cloudCounterConfig)
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 0)
            .thenEquals(CloudCounterState::viewShowsLoadingAndDisablesButtons, false)
            // Increment
            .on(CloudCounterWhen.UserTappedIncrementButton)
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 1)
            .thenEquals(CloudCounterState::viewShowsLoadingAndDisablesButtons, true)
            .on(CloudCounterWhen.NetworkPostCompleted(Dto(count = 1)))
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 1)
            .thenEquals(CloudCounterState::viewShowsLoadingAndDisablesButtons, false)
            // Decrement
            .on(CloudCounterWhen.UserTappedDecrementButton)
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 0)
            .thenEquals(CloudCounterState::viewShowsLoadingAndDisablesButtons, true)
            .on(CloudCounterWhen.NetworkPostCompleted(Dto(count = 0)))
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 0)
            .thenEquals(CloudCounterState::viewShowsLoadingAndDisablesButtons, false)
            // Invalid decrement (already at 0, no effect triggered)
            .on(CloudCounterWhen.UserTappedDecrementButton)
            .thenEquals(CloudCounterState::viewDisplaysTotalCount, 0)
            .runTest()
    }
}
```

## Outside a test: how effects actually run

`TestPlan` deliberately never runs real effects — but `createScope` (`statoscope.core`) does.
After `update` returns, the store launches every enqueued effect on a `CoroutineScope` (a
caller-supplied one, or an internal default), and feeds each result back through `send` when it
completes — fire-and-forget, no cancellation support yet. Because a launched effect can complete
on a different thread than whichever one called `send` originally, `send` is synchronized
internally so two completions (or a completion racing a caller's own `send`) can't corrupt state
concurrently.

Same acceptance criteria as Swift's and `statoscope-zustand`'s tutorials, same reducer contract
as Tutorial 01, now with a real, working path for async results to come back — and a first look
at how the two test DSLs across all of Statoscope's ports (Swift's `GIVEN`/`WHEN`/`THEN`,
`statoscope-zustand`'s `given`/`.when`, and this one) agree on the same rule: **effects are
simulated in tests, never actually run.**
