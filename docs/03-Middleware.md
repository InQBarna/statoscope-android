## Logging and error-handling middleware

`addMiddleware` intercepts every event a scope sends to *itself*, before its own `update()`
runs. It's a completely different mechanism from `MiddlewareReducer` (Swift's parent-reacts-to-
child composition, not yet built in this library): `addMiddleware` sees one scope's own events;
`MiddlewareReducer`-equivalent composition, whenever it lands here, will be about a parent
reacting to its children's events instead. Reach for `addMiddleware` for cross-cutting concerns
like logging or crash reporting on a single scope.

### Step 1 — the reducer

Same counter shape as Tutorial 01, with one addition: `ErrorCase`, an event that always throws —
enough to demonstrate a middleware catching an error, not just observing normal events.

```kotlin
import statoscope.core.Dependencies
import statoscope.core.EffectsState
import statoscope.core.ScopeConfig
import statoscope.core.createScope
/** Tutorial 03: same counter shape as Tutorial 01, plus an event that always throws. */
data class CounterState(val viewDisplaysTotalCount: Int = 0)

sealed interface CounterWhen {
    data object UserTappedIncrementButton : CounterWhen
    data object UserTappedDecrementButton : CounterWhen
    data object ErrorCase : CounterWhen // Will throw an error
}

fun counterUpdate(
    state: CounterState,
    action: CounterWhen,
    effects: EffectsState<CounterWhen>,
    dependencies: Dependencies
): CounterState {
    return when (action) {
        is CounterWhen.UserTappedIncrementButton ->
            state.copy(viewDisplaysTotalCount = state.viewDisplaysTotalCount + 1)
        is CounterWhen.UserTappedDecrementButton ->
            state.copy(viewDisplaysTotalCount = maxOf(0, state.viewDisplaysTotalCount - 1))
        is CounterWhen.ErrorCase ->
            throw IllegalStateException("Invalid state")
    }
}

val counterConfig = ScopeConfig(initial = CounterState(), update = ::counterUpdate)
```

> **Revised:** Tutorial 04 (Dependency Injection) needed every reducer to be able to resolve
> injected dependencies, so `ScopeConfig`'s `update` field grew a fourth parameter,
> `dependencies: Dependencies`. `counterUpdate` ignores it — same growth pattern documented in
> Tutorial 01: add the parameter, retrofit every existing example to accept (and ignore) it,
> document the change rather than silently rewriting history.

### Step 2 — intercepting every event

`addMiddleware` is fluent — it returns the same store, so it composes directly with
`createScope(...)`. The closure receives the store, the event, and a `forward` continuation:
calling `forward(action)` is what actually lets the event reach `update()`. Omitting the call
would block the event entirely — here we always call it, just after recording what came through.
Note this test builds the store directly (`createScope(...).addMiddleware { ... }`) and calls
`.send(...)` on it, rather than going through `given`/`.on` — `TestPlan` (Tutorial 01/02's
testing DSL) runs `update` directly and never touches `ScopeStore`, precisely so effects never
execute during a test. `addMiddleware` wraps `ScopeStore.send`, so exercising it means exercising
the real store.

```kotlin
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertTrue
class MiddlewareTest {

    @Test
    fun testMiddlewareInterceptsEvents() {
        val interceptedEvents = mutableListOf<CounterWhen>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                interceptedEvents += action
                forward(action)
            }

        counter.send(CounterWhen.UserTappedIncrementButton)
        counter.send(CounterWhen.UserTappedDecrementButton)

        assertEquals(2, interceptedEvents.size)
    }
}
```

### Step 3 — handling errors

Wrap `forward(action)` in `try`/`catch` to actually *react* to whatever `update` throws — `send`
itself already logs any uncaught exception and swallows it (see the built-in logging section
below), so without a middleware catching it here, a throwing event doesn't crash the caller, it
just silently disappears. This is exactly where crash reporting belongs in a real app: one
place, wrapping every event a scope processes, rather than a `try`/`catch` scattered through
every call site that might send something risky.

```kotlin
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertTrue
class MiddlewareTest {

    @Test
    fun testMiddlewareInterceptsEvents() {
        val interceptedEvents = mutableListOf<CounterWhen>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                interceptedEvents += action
                forward(action)
            }

        counter.send(CounterWhen.UserTappedIncrementButton)
        counter.send(CounterWhen.UserTappedDecrementButton)

        assertEquals(2, interceptedEvents.size)
    }

    @Test
    fun testMiddlewareCanHandleErrors() {
        val errorsCaught = mutableListOf<Throwable>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                try {
                    forward(action)
                } catch (error: Throwable) {
                    errorsCaught += error
                }
            }

        counter.send(CounterWhen.ErrorCase)

        assertEquals(1, errorsCaught.size)
        assertTrue(errorsCaught.first() is IllegalStateException)
    }
}
```

### Step 4 — logging, and the state still updates normally

A middleware doesn't change what `update` does — it just gets a look at the event first. After
`send`, `counter.state` reflects the same result it would without any middleware attached at
all.

```kotlin
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertTrue
class MiddlewareTest {

    @Test
    fun testMiddlewareInterceptsEvents() {
        val interceptedEvents = mutableListOf<CounterWhen>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                interceptedEvents += action
                forward(action)
            }

        counter.send(CounterWhen.UserTappedIncrementButton)
        counter.send(CounterWhen.UserTappedDecrementButton)

        assertEquals(2, interceptedEvents.size)
    }

    @Test
    fun testMiddlewareCanHandleErrors() {
        val errorsCaught = mutableListOf<Throwable>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                try {
                    forward(action)
                } catch (error: Throwable) {
                    errorsCaught += error
                }
            }

        counter.send(CounterWhen.ErrorCase)

        assertEquals(1, errorsCaught.size)
        assertTrue(errorsCaught.first() is IllegalStateException)
    }

    @Test
    fun testMiddlewareCanLogEvents() {
        val logs = mutableListOf<String>()

        val counter = createScope(counterConfig)
            .addMiddleware { _, action, forward ->
                logs += "Event: $action"
                forward(action)
            }

        counter.send(CounterWhen.UserTappedIncrementButton)

        assertEquals(1, counter.state.viewDisplaysTotalCount)
        assertTrue(logs.contains("Event: UserTappedIncrementButton"))
    }
}
```

Only one middleware is supported per store for now — a second `addMiddleware` call replaces the
first rather than chaining. Swift's `addMiddleWare` supports stacking several; nothing in
`statoscope-kotlin` exercises that yet, so it isn't built.

## Built-in Library logging

The error reporting added above is exactly what `addMiddleware` is for. But wiring up your own
logging middleware on every scope you create gets repetitive — and Statoscope already has a
built-in feature for it. This ports Swift's `StatoscopeLogger`
(`Sources/Statoscope/Logging/StatoscopeLogger.swift`) and `statoscope-zustand`'s equivalent
(`src/logger.ts`) directly: a single global switchboard (`statoscope.core.StatoscopeLogger`),
gated by category rather than attached per scope. `injection` isn't ported as a category —
Kotlin's `Dependencies.resolve` (Tutorial 04) always falls back to a key's own default rather
than failing, so there's no ancestor-tree resolution failure to log, the same simplification
`statoscope-zustand` made for the same reason.

`send`, `update`, and effect launch/completion are already wired into it — nothing to attach.
Turning on a category makes every scope's activity visible, not just one you happened to
instrument.

### Step 1 — enable it globally

```kotlin
import statoscope.core.LogLevelSets
import statoscope.core.StatoscopeLogger
private fun enableVerboseLogging() {
    StatoscopeLogger.logLevel = LogLevelSets.all
}
```

`LogLevelSets.all` turns on `errors`, `when`, `effects`, and `stateDiff` — everything except the
full-state dumps under `state`, reserved for `LogLevelSets.verbose`. The default, before this
call, is `{errors}` only: framework exceptions are always visible, everything else is opt-in.

### Step 2 — see what gets captured

`StatoscopeLogger.logReplacement` redirects output anywhere — to `println` (the default), to a
test's own capture list, or eventually to Android's `Log.d` once this library grows an Android
target. The test below installs a capturing replacement and exercises all three categories
`LogLevelSets.all` turns on: `when` (the increment/decrement events), `stateDiff` (one changed
line per field), and `errors` (the `ErrorCase` exception — logged, then swallowed by `send`
itself, exactly like the `addMiddleware` error-handling section above describes; the built-in
logger only observes, it never recovers anything on its own).

```kotlin
import statoscope.core.LogLevelSets
import statoscope.core.StatoscopeLogger

import kotlin.test.AfterTest
import statoscope.core.LogLevel
class BuiltInLoggingTest {

    @AfterTest
    fun resetLogger() {
        StatoscopeLogger.logLevel = setOf(LogLevel.Errors)
        StatoscopeLogger.logReplacement = null
    }

    @Test
    fun testBuiltInLoggingCapturesEventsStateDiffsAndErrors() {
        enableVerboseLogging()
        val logs = mutableListOf<String>()
        StatoscopeLogger.logReplacement = { _, message -> logs += message }

        val counter = createScope(counterConfig)
        counter.send(CounterWhen.UserTappedIncrementButton)
        counter.send(CounterWhen.UserTappedDecrementButton)
        // send() swallows this exception after logging it — it never reaches this call site.
        // Use addMiddleware (the previous section) instead of relying on this if you need to
        // actually react to the error, not just see it in the log.
        counter.send(CounterWhen.ErrorCase)

        assertTrue(logs.any { it.contains("UserTappedIncrementButton") })
        assertTrue(logs.any { it.contains("- ") && it.contains("viewDisplaysTotalCount: 0") })
        assertTrue(logs.any { it.contains("+ ") && it.contains("viewDisplaysTotalCount: 1") })
        assertTrue(logs.any { it.contains("Exception on send") })
    }
}
```

`resetLogger()` matters as much as the test itself: `StatoscopeLogger` is global, mutable,
process-wide state, so a test that installs a `logReplacement` and forgets to remove it leaks
into whatever test runs next in the same process. Every logging test in this project's own
test suite (`statoscope.core.StatoscopeLoggerTest`, `ScopeStoreLoggingTest`) follows the same
`@AfterTest` discipline.

A non-null `logReplacement` receives *every* category regardless of `logLevel` — installing a
replacement means "everything is enabled," matching Swift's rule exactly; the replacement itself
decides what to do with each level. `logLevel` alone (no replacement) gates what reaches the
default `println`/`System.err.println` sink.

This is a different mechanism from `MiddlewareReducer` (a parent reacting to a child's events,
not yet built in this library): the built-in logger sees every event *every* scope sends to
itself, process-wide, with no per-scope opt-out — the closest thing to "identifying one scope in
a shared log stream" is the `"TypeName (identityHash):"` prefix each log line carries. Reach for
`addMiddleware` when you need per-scope control (block an event, redirect just one scope's
errors); reach for `StatoscopeLogger` for the cross-cutting, "I want to see everything" case.
